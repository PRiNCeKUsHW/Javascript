::: analogy An API works like a restaurant
> Let's start with a simple picture: a restaurant.
- 🧑 You order from the menu => The client (browser, mobile app) sends a **request**
> You sit down and order from the menu. On the web, the client, like a browser or a mobile app, sends a request.
- 📝 The waiter takes it to the kitchen => The **API** receives it and routes it
> The waiter takes your order to the kitchen. That's the API. It receives the request and sends it to the right place.
- 👨‍🍳 The kitchen cooks the dish => Your **Python code** and database do the work
> The kitchen does the real work. That's your Python code, usually talking to a database.
- 🍽️ The waiter brings your food => The API returns a **JSON response**
> And the waiter brings your food back. The API returns a response, usually as JSON.
L> So the menu is like the list of things I'm allowed to ask for?
> Exactly. Those are called endpoints, and you'll build your first ones in a few minutes.
:::

::: concept What's inside a request?
visual: client-server
- 🔗 A **URL**: where it goes, like `/users/42`
> Every request has a few parts. First, a URL that says where it's going, like slash users slash forty two.
- 🏷️ A **method**: GET reads, POST creates, PUT and PATCH update, DELETE removes
> Second, a method. GET reads data, POST creates something new, PUT and PATCH update it, and DELETE removes it.
- 📦 **Headers** and an optional JSON **body**
> Third, headers with extra information, and sometimes a body with JSON data.
- ✅ The answer: a **status code** like 200, plus JSON
> The server answers with a status code, like two hundred for OK, plus the data.
L> Why JSON, though? Why not just send Python objects?
> Because the client might be written in JavaScript, Swift or Kotlin. JSON is the common language every platform understands.
:::

::: concept Why FastAPI?
visual: speed
- ⚡ **Fast to run**: built on Starlette and ASGI
> FastAPI is fast to run. It's built on Starlette and A S G I, which puts it among the fastest Python frameworks.
- ✍️ **Fast to write**: type hints give you validation and autocomplete
> It's also fast to write. You add normal Python type hints, and you get data validation and editor autocomplete for free.
- 📖 **Automatic docs** generated from your code
> And it writes your documentation for you, straight from your code.
- 🏢 Used in production at Microsoft, Uber and Netflix
> That's why teams at companies like Microsoft, Uber and Netflix use it in production.
L> Is it hard to learn?
> Not at all. If you know Python functions and type hints, you already know half of FastAPI.
:::

::: flow How a request reaches your code
> Here's the journey of one request.
- 📱 Client
> A client sends the request.
- 🦄 Uvicorn (ASGI server)
> Uvicorn receives it. Uvicorn is an A S G I server, which handles the networking.
- ⚡ FastAPI app
> It passes the request to your FastAPI app.
- 🐍 Your function
> FastAPI looks at the URL and the method, and calls the matching Python function. We call it a path operation function.
- 📦 JSON response
> Whatever your function returns, FastAPI turns into JSON and sends back to the client.
:::

::: code main.py | Your first FastAPI app
```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/")
def read_root():
    return {"message": "Hello, FastAPI!"}


@app.get("/items/{item_id}")
def read_item(item_id: int):
    return {"item_id": item_id}
```
@1 > Let's write our first app. Import the FastAPI class.
@3 > Create an instance called app. This object is your whole application.
@6 > This decorator says: when someone sends a GET request to slash, run the function below.
@7-8 > The function returns a normal Python dictionary, and FastAPI converts it to JSON for you.
@11-12 > The second route is smarter. The part in curly braces, item id, is a path parameter.
@12-13 > And because of the int type hint, FastAPI converts it to a number and validates it.
@all L> That's it? Thirteen lines?
@all > That's it. Thirteen lines, and you have a working API.

::: mistake The type hint you forgot
```python
@app.get("/items/{item_id}")
def read_item(item_id):
    return {"next_id": item_id + 1}
```
```python
@app.get("/items/{item_id}")
def read_item(item_id: int):
    return {"next_id": item_id + 1}
```
@wrong > Here's a mistake beginners make all the time. No type hint on item id.
L> It looks fine to me. What goes wrong?
> Without a hint, item id arrives as a string. A string plus one raises a TypeError, and the client gets a five hundred server error.
@right > Add int, and FastAPI converts and validates it for you. Bad input now gets a clean four twenty two instead of a crash.
:::

::: concept fastapi dev vs fastapi run
- 🧪 `fastapi dev main.py`: auto reload, localhost only, for development
> fastapi dev is for development. It reloads on every change, and it only listens on your own machine.
- 🚀 `fastapi run main.py`: no reload, listens on all interfaces, for servers
> fastapi run is for production. No reloading, and it listens on all network interfaces, which servers and containers need.
- 🦄 Both start **Uvicorn** under the hood
> Both start Uvicorn under the hood.
- 🔧 Change the port with `--port 9000`
> And you can change the port with dash dash port.
L> So I should never use dev mode on a server?
> Right. Auto reload watches files and costs performance. In level twelve we'll set up production properly, with workers and Docker.

::: interview junior
q: What is FastAPI, and why would you choose it over Flask?
- A modern Python framework for APIs, driven by type hints
> FastAPI is a modern Python framework for building APIs, and it's driven by type hints.
- Built-in validation and serialization through Pydantic
> Validation and serialization are built in through Pydantic, while Flask usually needs extra libraries for that.
- Automatic OpenAPI docs and native async on ASGI
> It generates OpenAPI docs automatically, and it supports async natively because it runs on A S G I.
- Flask is still fine for simple sync apps and HTML pages
> Flask is still a good choice for simple sync apps or server rendered pages, but for modern APIs FastAPI is more productive.
M> Great answer, Leo. Showing that you know the trade-offs always impresses interviewers.

::: interview junior
q: What is the difference between WSGI and ASGI?
qsay: What is the difference between W S G I and A S G I?
- **WSGI**: synchronous, one request per worker at a time
> W S G I is the older, synchronous standard. A worker handles one request at a time.
- **ASGI**: asynchronous, one worker serves others while waiting on I/O
> A S G I is asynchronous. While one request waits for the database or the network, the same worker can serve other requests.
- ASGI also supports WebSockets and long-lived connections
> A S G I also supports WebSockets and other long lived connections.
- FastAPI runs on ASGI servers such as Uvicorn
> FastAPI is an A S G I app, served by Uvicorn.
:::

::: interview mid
q: Where does FastAPI's request validation come from, and what happens when it fails?
- Type hints are turned into Pydantic validation
> FastAPI turns your type hints into Pydantic validation.
- Input is parsed and converted before your function runs
> Input is parsed and converted, for example the string forty two becomes the number forty two, before your function runs.
- On failure: **422** with a `detail` list of type, loc and msg
> If validation fails, the client gets a four twenty two with a detail list explaining each error.
- Invalid data never reaches your business logic
> So invalid data never reaches your business logic.
:::

::: interview mid
q: What is the difference between `fastapi dev` and `fastapi run`?
qsay: What is the difference between fastapi dev and fastapi run?
- `dev`: auto reload, binds to 127.0.0.1, for local development
> fastapi dev reloads on every change and binds to localhost, so it's for local development only.
- `run`: no reload, binds to 0.0.0.0, for servers and containers
> fastapi run doesn't reload and listens on all interfaces, which is what servers and Docker containers need.
- Both start Uvicorn; production also needs workers and a reverse proxy
> Both start Uvicorn. In production you'd also add multiple workers and a reverse proxy in front.
