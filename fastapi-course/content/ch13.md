::: code app/core/codes.py | Short codes with base62
```python
ALPHABET = string.digits + string.ascii_lowercase + string.ascii_uppercase


def encode_base62(n: int) -> str:
    if n == 0:
        return ALPHABET[0]
    out = []
    while n:
        n, rem = divmod(n, 62)
        out.append(ALPHABET[rem])
    return "".join(reversed(out))
```
```output
>>> encode_base62(100_000)
'q0U'
>>> encode_base62(10**12)    # a trillion links: still 7 characters
'hBxM5A4'
```
@1 > Sixty two characters: digits, lowercase and uppercase letters.
@4-11 > We convert the link's database ID to base sixty two, just like converting to binary, but with sixty two digits.
@out > ID one hundred thousand becomes q zero U. And a trillion links still fit in seven characters.
@out L> And because IDs are unique, codes are unique too. No collision checks!
@out > Exactly. The trade-off is that codes are guessable, in order. If links are private, use random codes and check for collisions instead.
:::

::: code app/api/v1/links.py | The redirect endpoint
```python
class LinkIn(BaseModel):
    url: HttpUrl


@router.get("/{code}")
async def follow(code: str, session: SessionDep, redis: RedisDep, background: BackgroundTasks):
    url = await redis.get(f"link:{code}")
    if url is None:
        link = await get_link_or_404(session, code)
        url = link.url
        await redis.set(f"link:{code}", url, ex=3600)
    background.add_task(count_click, code)
    return RedirectResponse(url, status_code=307)
```
@1-2 > HttpUrl validates links. Something like javascript colon alert gets rejected with four twenty two, so nobody can use your domain to run scripts.
@6-10 > Look in Redis first. On a miss, load from the database, and cache for an hour.
@11 > Count the click in the background, so the redirect isn't slowed down.
@12 > And redirect with three oh seven.
@all L> Why not three oh one, permanent redirect?
@all > Browsers cache three oh ones forever, so later clicks never reach your server, and your analytics break. Three oh seven keeps every click visible.

::: code app/core/slugs.py | Readable, unique slugs
```python
def slugify(title: str) -> str:
    text = unicodedata.normalize("NFKD", title).encode("ascii", "ignore").decode()
    return re.sub(r"[^a-z0-9]+", "-", text.lower()).strip("-")


def unique_slug(title: str, taken: set[str]) -> str:
    base = slug = slugify(title)
    n = 2
    while slug in taken:
        slug = f"{base}-{n}"
        n += 1
    return slug
```
```output
slugify("FastAPI in 2026: Café Edition!")  → "fastapi-in-2026-cafe-edition"
unique_slug("Hello World", {"hello-world", "hello-world-2"})  → "hello-world-3"
```
@1-3 > Slugify turns accents into plain letters, lowercases, and replaces everything else with dashes.
@6-11 > If the slug is taken, add a number, two, three, and so on.
@out L> And the database should still have a unique constraint on slug, right?
@out > Always. The code makes nice slugs, and the constraint guarantees no duplicates, even with two requests at the same time.

::: mistake Storing money as float
```python
class Product(Base):
    price: Mapped[float]          # 0.1 + 0.2 = 0.30000000000000004

total = sum(item.price * item.qty for item in cart)
```
```python
class Product(Base):
    price_cents: Mapped[int]      # ₹2,499.00 → 249900

total_cents = sum(i.price_cents * i.qty for i in cart)
# or: Numeric(10, 2) in the DB + Decimal in Python
```
@wrong > Floats can't represent most decimal numbers exactly. Zero point one plus zero point two isn't zero point three.
L> It's only a tiny difference, though.
> Multiply it by a million orders, and the accountants will find you. Rounding errors in money are real bugs.
@right > Store money as an integer number of the smallest unit, like paise or cents. Or use Numeric in the database and Decimal in Python. Never float.
:::

::: mistake The overselling race condition
```python
async def reserve_stock(session, product_id, qty):
    product = await session.get(Product, product_id)
    if product.stock < qty:
        return False
    product.stock -= qty       # two requests both get here!
    return True
```
```python
async def reserve_stock(session, product_id, qty):
    result = await session.execute(
        update(Product)
        .where(Product.id == product_id, Product.stock >= qty)
        .values(stock=Product.stock - qty)
    )
    return result.rowcount == 1
```
@wrong > This looks correct. Read the stock, check it, subtract. But two customers can buy the last keyboard at the same moment. Both read one, both pass the check.
L> Does that really happen?
> I tested it. Two buyers, one keyboard in stock. Both were told they bought it. That's an angry customer, and a refund.
@right > The fix is one atomic update. The check and the subtract happen together, inside the database. If the row didn't change, there wasn't enough stock. In my test, five buyers raced for one keyboard, and exactly one got it.
:::

::: code app/api/v1/orders.py | Idempotency keys: safe retries
```python
@router.post("/orders", status_code=201)
async def place_order(data: OrderIn, session: SessionDep, user: CurrentUser,
                      idempotency_key: Annotated[str, Header(min_length=8, max_length=64)]):
    if existing := await session.scalar(
            select(Order.id).where(Order.idempotency_key == idempotency_key)):
        return {"order_id": existing, "replayed": True}
    if not await reserve_stock(session, data.product_id, data.quantity):
        raise HTTPException(409, "Out of stock")
    order = await create_order(session, user, data, idempotency_key)
    await session.commit()
    return {"order_id": order.id, "total_cents": order.total_cents, "replayed": False}
```
```output
POST /orders  Idempotency-Key: a1b2c3d4-retry  → 201 {"order_id": 1, "total_cents": 499800}
POST /orders  Idempotency-Key: a1b2c3d4-retry  → 201 {"order_id": 1, "replayed": true}
```
@1-3 > The client sends a unique Idempotency Key header with each new order.
@4-6 > If we've seen that key before, return the same order. Don't create a second one.
@7-8 > Otherwise, reserve stock atomically, or four oh nine.
@9-11 > Then create the order and commit. The key has a unique constraint too.
@out L> So if the phone loses network and the app retries, I'm not charged twice.
@out > Exactly. Stripe and every payment API work this way.
