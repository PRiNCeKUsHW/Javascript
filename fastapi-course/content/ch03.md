::: analogy Pydantic is like the admission desk at college
> Pydantic को समझने के लिए college admission का example लेते हैं।
- 📝 The admission form lists every field => A Pydantic **model** declares the fields
> Admission form में हर field पहले से लिखा होता है, नाम, उम्र, email। Pydantic model भी यही बताता है कि data में कौन से fields होंगे।
- 🔍 The clerk checks each field => Pydantic **validates** every value
> Desk पर बैठा clerk हर field check करता है। Pydantic भी हर value validate करता है।
- 🔢 Age "18" is written down as the number 18 => It **converts** types: `"18"` → `18`
> अगर आपने age को text में लिखा, तो clerk उसे number मान लेता है। Pydantic भी types convert करता है।
- ❌ Form returned with every mistake marked => Invalid data → **422** listing all errors
> और गलती हो, तो form वापस आता है, हर mistake mark करके। Pydantic भी सारी errors एक साथ बताता है।

::: code students.py | Your first request body
```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Student(BaseModel):
    name: str
    age: int
    email: str
    city: str | None = None


@app.post("/students")
def create_student(student: Student):
    return {"message": f"Welcome {student.name}!", "data": student}
```
@2 > सबसे पहले pydantic से BaseModel import कीजिए।
@7-11 > फिर एक class बनाइए जो BaseModel से inherit करे। हर attribute एक field है, अपने type के साथ। city optional है।
@14 > अब POST route पर parameter का type Student रख दिया। बस इतने से FastAPI समझ जाती है कि ये data request body से आएगा।
@15-16 > Function के अंदर student एक proper Python object है, तो आप student dot name जैसे use कर सकते हैं, dictionary keys की ज़रूरत नहीं।

::: concept Where does each parameter come from?
- Name is in the path → **path** parameter
> FastAPI एक simple rule follow करती है। Parameter का नाम path में है, तो वो path parameter।
- Simple type (`int`, `str`, `bool`) → **query** parameter
> Simple type है, जैसे int या str, तो query parameter।
- Pydantic model → **request body** (JSON)
> और Pydantic model है, तो request body।
- You can mix all three in one endpoint
> आप तीनों को एक ही endpoint में mix भी कर सकते हैं, FastAPI सबको सही जगह से उठा लेगी।
:::

::: code students.py | Field rules and EmailStr
```python
from pydantic import BaseModel, EmailStr, Field


class Student(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    age: int = Field(ge=16, le=60)
    email: EmailStr
    skills: list[str] = Field(default_factory=list, max_length=10)
```
@1 > अब rules लगाते हैं। इसके लिए Field और EmailStr import कीजिए।
@5 > Name कम से कम दो और ज़्यादा से ज़्यादा पचास characters का।
@6 > Age सोलह से साठ के बीच।
@7 > EmailStr असली email format check करता है। ये fastapi standard install के साथ ही आता है।
@8 > Skills एक list है, जिसमें ज़्यादा से ज़्यादा दस items। default factory list का मतलब, हर student को अपनी नई खाली list मिलेगी।

::: code signup.py | Custom validators
```python
class SignUp(BaseModel):
    username: str
    password: str
    confirm_password: str

    @field_validator("username")
    @classmethod
    def no_spaces(cls, v: str) -> str:
        if " " in v:
            raise ValueError("username must not contain spaces")
        return v.lower()

    @model_validator(mode="after")
    def passwords_match(self):
        if self.password != self.confirm_password:
            raise ValueError("passwords do not match")
        return self
```
@7-12 > कभी कभी built in rules काफ़ी नहीं होते। field validator से एक field के लिए अपना logic लिख सकते हैं। ये pydantic से import होता है।
@10-11 > Username में space हो, तो ValueError raise कीजिए। Pydantic उसे four twenty two error में बदल देगा।
@12 > और जो return करेंगे, वही final value बनेगी, यहाँ lowercase username।
@14-18 > Model validator पूरे model को एक साथ देखता है। जब दो fields compare करने हों, जैसे password और confirm password, तब ये use होता है।

::: code schemas.py | Separate schemas for create, read and update
```python
class TaskBase(BaseModel):
    title: str = Field(min_length=1, max_length=100)
    done: bool = False


class TaskCreate(TaskBase):
    pass


class TaskRead(TaskBase):
    id: int


class TaskUpdate(BaseModel):
    title: str | None = None
    done: bool | None = None
```
@1-3 > Production apps में एक model से काम नहीं चलता। Common fields एक Base class में रखिए।
@6-7 > TaskCreate वो है जो client भेजता है। इसमें id नहीं होती, क्योंकि id server बनाता है।
@10-11 > TaskRead वो है जो हम वापस भेजते हैं, id के साथ।
@14-16 > और TaskUpdate में सारे fields optional हैं, क्योंकि update में client कुछ ही fields बदलना चाहता है।

::: code tasks.py | PATCH: update only what was sent
```python
TASKS: dict[int, TaskRead] = {}


@app.patch("/tasks/{task_id}")
def update_task(task_id: int, changes: TaskUpdate) -> TaskRead:
    stored = TASKS[task_id]
    updates = changes.model_dump(exclude_unset=True)
    TASKS[task_id] = stored.model_copy(update=updates)
    return TASKS[task_id]
```
@4-5 > PATCH का मतलब partial update। Client सिर्फ वही भेजता है जो बदलना है।
@7 > असली trick ये line है। exclude unset true से सिर्फ वो fields मिलती हैं जो client ने सच में भेजीं।
@8 > फिर model copy से पुराने data पर सिर्फ वही बदलाव लगाए। बाकी fields जैसी थीं, वैसी रहीं।
:::

::: concept Pydantic v1 → v2 cheat sheet
- `.dict()` → `.model_dump()` and `.json()` → `.model_dump_json()`
> अगर आप पुराना code या tutorials देखें, तो ये names बदल गए हैं। dict अब model dump है।
- `parse_obj()` → `model_validate()`
> parse obj अब model validate है।
- `@validator` → `@field_validator` / `@model_validator`
> validator की जगह field validator और model validator।
- `class Config` / `orm_mode` → `model_config` / `from_attributes=True`
> और Config class की जगह model config, जिसमें orm mode अब from attributes कहलाता है।
:::

::: recap
- A Pydantic model parameter is read from the JSON body
> Recap। Pydantic model वाला parameter JSON body से आता है।
- `Field()` adds rules; `EmailStr` checks emails
> Field से rules लगते हैं, और EmailStr email check करता है।
- Models can nest; lists are validated item by item
> Models nested हो सकते हैं, और lists का हर item check होता है।
- `field_validator` for one field, `model_validator` for cross-field rules
> एक field के लिए field validator, और कई fields के लिए model validator।
- Use separate Create / Read / Update schemas and `exclude_unset` for PATCH
> और production में अलग create, read और update schemas, साथ में PATCH के लिए exclude unset।
:::

qsay: सवाल नंबर दो. price को zero से बड़ा, और name को तीन से चालीस characters का बनाइए।

```python
class Product(BaseModel):

```
- `gt` = greater than (strict), `ge` = greater or equal
> gt का मतलब strictly greater than, इसलिए zero भी reject होगा। ge होता तो zero allowed होता।

::: practice
q: What is wrong with using `changes.model_dump()` without `exclude_unset=True` in a PATCH endpoint?
qsay: सवाल नंबर तीन. PATCH endpoint में exclude unset के बिना model dump use करने में क्या problem है?
a:
- Fields the client didn't send come back as `None`
> जो fields client ने नहीं भेजीं, वो भी None बनकर आ जाएँगी।
- Those `None`s overwrite real data: a silent data-loss bug
> और वो None आपके असली data को overwrite कर देंगे। ये एक silent data loss bug है, जो production में बहुत महँगा पड़ता है।
:::

::: practice
q: Write a validator that trims spaces and title-cases `name` (" riya sharma " → "Riya Sharma").
qsay: सवाल नंबर चार. एक validator लिखिए जो name के extra spaces हटाए और उसे title case में कर दे।
a:
```python
class Person(BaseModel):
    name: str

    @field_validator("name")
    @classmethod
    def clean_name(cls, v: str) -> str:
        return v.strip().title()
```
- A validator can **transform** the value, not just reject it
> Validator सिर्फ reject नहीं करता, value को साफ़ भी कर सकता है। जो return करोगे, वही store होगा।

::: practice
q: An `int` field receives `"21"`. Is that an error? What about `"twenty"`?
qsay: सवाल नंबर पाँच. एक int field में string twenty one आए, तो error है या नहीं? और अगर spelling में twenty लिखा हो तो?
a:
- `"21"` is accepted and converted to `21` (lax mode)
> String twenty one accept होगा और number twenty one बन जाएगा। इसे lax mode कहते हैं।
- `"twenty"` → 422 `int_parsing`
> लेकिन twenty को number में बदल नहीं सकते, तो four twenty two।
- Need no conversion at all? Use `Field(strict=True)`
> और अगर आपको conversion बिल्कुल नहीं चाहिए, तो Field में strict true लगाइए।

::: code schemas.py | Project solution: the input schema
```python
class Address(BaseModel):
    city: str
    pincode: str = Field(pattern=r"^\d{6}$")


class StudentCreate(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    age: int = Field(ge=16, le=60)
    email: EmailStr
    address: Address
    password: str = Field(min_length=8)
    confirm_password: str

    @model_validator(mode="after")
    def passwords_match(self):
        if self.password != self.confirm_password:
            raise ValueError("passwords do not match")
        return self
```
@1-3 > Solution में पहले Address model, छह digit pincode के साथ।
@6-12 > StudentCreate में सारे rules, और password कम से कम आठ characters।
@14-18 > और model validator दोनों passwords compare करता है।

::: code main.py | Project solution: hiding the password
```python
class StudentRead(BaseModel):
    id: int
    name: str
    email: EmailStr
    address: Address


DB: dict[int, dict] = {}


@app.post("/students", response_model=StudentRead, status_code=201)
def register(student: StudentCreate):
    new_id = len(DB) + 1
    DB[new_id] = {"id": new_id, **student.model_dump(exclude={"confirm_password"})}
    return DB[new_id]
```
@1-5 > StudentRead में password field है ही नहीं।
@11 > और route पर response model StudentRead लगाया। अब हम पूरी dictionary भी return करें, तो FastAPI सिर्फ StudentRead वाले fields ही भेजेगी।
@12-15 > अभी data एक dictionary में save हो रहा है। Real database Level six में आएगा। Response model के बारे में detail में अगले level में बात करेंगे।

::: interview junior
q: What is Pydantic, and why does FastAPI use it?
- A data validation library driven by Python type hints
> Pydantic एक data validation library है, जो Python type hints से काम करती है।
- Parses, converts and validates incoming JSON into typed objects
> ये incoming JSON को parse, convert और validate करके typed Python objects बना देती है।
- FastAPI uses it for request bodies, responses and the OpenAPI schema
> FastAPI इसे request bodies, responses और OpenAPI docs, तीनों के लिए use करती है।
- Its core is written in Rust, so validation is fast
> और Pydantic version two का core Rust में लिखा है, इसलिए validation बहुत fast है।
:::

::: interview junior
q: How does FastAPI decide whether a parameter comes from the path, the query string or the body?
- Name appears in the path template → path
> Parameter का नाम path में है, तो path।
- Singular type like `int` or `str` → query
> int या str जैसा simple type है, तो query।
- Pydantic model → JSON body
> Pydantic model है, तो body।
- Override explicitly with `Path()`, `Query()`, `Body()`, `Header()`, `Cookie()`
> और ज़रूरत हो तो Path, Query, Body, Header या Cookie से explicitly बता सकते हैं।
:::

::: interview mid
q: Why use separate models like `UserCreate` and `UserRead` instead of one `User` model?
qsay: Why use separate models like UserCreate and UserRead, instead of one User model?
- Input and output need different fields: clients never send `id`
> Input और output में fields अलग होते हैं। Client id नहीं भेजता, server बनाता है।
- Secrets like passwords must never be returned
> Password जैसी secret चीज़ें response में कभी नहीं जानी चाहिए।
- Update models make every field optional
> Update model में सारे fields optional होते हैं।
- Clear contracts and docs; changing one doesn't break the others
> इससे API का contract साफ़ रहता है, और एक model बदलने से बाकी नहीं टूटते।
:::

::: interview mid
q: How do you implement a PATCH (partial update) correctly in FastAPI?
- An update schema with all fields optional
> एक update schema, जिसमें सारे fields optional हों।
- `model_dump(exclude_unset=True)` to get only the fields that were sent
> फिर model dump exclude unset true से सिर्फ वही fields लीजिए जो client ने भेजीं।
- Apply them onto the stored object (`model_copy(update=...)` or set attributes)
> और उन्हें stored object पर लगाइए।
- Without it, missing fields become `None` and wipe real data
> इसके बिना missing fields None बनकर असली data मिटा देती हैं।
:::

::: interview senior
q: What changed from Pydantic v1 to v2 that matters for a FastAPI codebase?
- Rust core (`pydantic-core`): much faster validation and serialization
> Version two का core Rust में है, इसलिए validation और serialization काफ़ी fast हो गए।
- Renamed APIs: `model_dump`, `model_validate`, `field_validator`, `model_config`
> कई APIs के नाम बदले, जैसे model dump, model validate, field validator और model config।
- `from_attributes` replaces `orm_mode`; strict mode is available
> orm mode अब from attributes है, और strict mode भी मिलता है।
- Migration: upgrade deps, run tests, fix deprecation warnings step by step
> Migration के लिए dependencies upgrade कीजिए, tests चलाइए, और deprecation warnings एक एक करके ठीक कीजिए। Senior candidate से ये practical migration plan expect किया जाता है।
:::
