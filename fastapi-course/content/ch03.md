::: code students.py | Field rules and EmailStr
```python
from pydantic import BaseModel, EmailStr, Field


class Student(BaseModel):
    name: str = Field(min_length=2, max_length=50)
    age: int = Field(ge=16, le=60)
    email: EmailStr
    skills: list[str] = Field(default_factory=list, max_length=10)
```
```output
{"name": "R", "age": 12, "email": "nope"}  ->  422 with 3 errors:
  name: String should have at least 2 characters
  age: Input should be greater than or equal to 16
  email: value is not a valid email address
```
@1 > Now let's add rules. Import Field and EmailStr.
@5 > The name must be two to fifty characters.
@6 > Age must be between sixteen and sixty.
@7 > EmailStr checks for a real email format. It comes with the fastapi standard install.
@8 > Skills is a list of at most ten items. default factory list gives every student their own fresh empty list.
@out > Send bad data, and you get all three problems in one response, each with a clear message.

::: code signup.py | Custom validators
```python
class SignUp(BaseModel):
    username: str
    password: str
    confirm_password: str

    @field_validator("username")
    @classmethod
    def no_spaces(cls, v: str) -> str:
        if " " in v:
            raise ValueError("username must not contain spaces")
        return v.lower()

    @model_validator(mode="after")
    def passwords_match(self):
        if self.password != self.confirm_password:
            raise ValueError("passwords do not match")
        return self
```
@6-11 > Sometimes built in rules aren't enough. A field validator runs your own logic for one field. You import it from pydantic.
@9-10 > If the username has a space, raise a ValueError. Pydantic turns it into a four twenty two.
@11 > Whatever you return becomes the final value, here the lowercase username.
@13-17 > A model validator sees the whole model at once. Use it when you compare fields, like password and confirm password.
@13 L> Why mode after?
@13 > After means it runs once every field is already validated and converted, so you're comparing clean values.
:::

::: code schemas.py | Separate schemas for create, read and update
```python
class TaskBase(BaseModel):
    title: str = Field(min_length=1, max_length=100)
    done: bool = False


class TaskCreate(TaskBase):
    pass


class TaskRead(TaskBase):
    id: int


class TaskUpdate(BaseModel):
    title: str | None = None
    done: bool | None = None
```
@1-3 > Production apps never use one model for everything. Shared fields go in a base class.
@6-7 > TaskCreate is what clients send. It has no id, because the server creates the id.
@10-11 > TaskRead is what we send back, including the id.
@14-16 > And TaskUpdate makes every field optional, because an update usually changes just a few fields.
L> Isn't that a lot of classes for one task?
> It looks like more code, but each class is a clear contract. And it prevents the bug I'm about to show you.

::: mistake Silent data loss in PATCH
```python
@app.patch("/tasks/{task_id}")
def update_task(task_id: int, changes: TaskUpdate):
    stored = TASKS[task_id]
    updates = changes.model_dump()
    TASKS[task_id] = stored.model_copy(update=updates)
    return TASKS[task_id]
```
```python
@app.patch("/tasks/{task_id}")
def update_task(task_id: int, changes: TaskUpdate):
    stored = TASKS[task_id]
    updates = changes.model_dump(exclude_unset=True)
    TASKS[task_id] = stored.model_copy(update=updates)
    return TASKS[task_id]
```
@wrong > The client sends only done equals true. But model dump returns every field, so the title comes back as None.
L> And then the None overwrites the real title?
> Exactly. The task loses its title, no error is raised, and nobody notices until a customer complains.
@right > Add exclude unset equals true. Now only the fields the client actually sent are applied, and everything else stays as it was.
:::

::: concept Pydantic v1 → v2 cheat sheet
- 🔁 `.dict()` → `.model_dump()`, `.json()` → `.model_dump_json()`
> If you read older tutorials, the names have changed. dict is now model dump.
- 🔁 `parse_obj()` → `model_validate()`
> parse obj is now model validate.
- 🔁 `@validator` → `@field_validator` / `@model_validator`
> validator became field validator and model validator.
- 🔁 `class Config` / `orm_mode` → `model_config` / `from_attributes=True`
> And the Config class became model config, where orm mode is now called from attributes.
:::

::: code main.py | Project solution: hiding the password
```python
class StudentRead(BaseModel):
    id: int
    name: str
    email: EmailStr
    address: Address


DB: dict[int, dict] = {}


@app.post("/students", response_model=StudentRead, status_code=201)
def register(student: StudentCreate):
    new_id = len(DB) + 1
    DB[new_id] = {"id": new_id, **student.model_dump(exclude={"confirm_password"})}
    return DB[new_id]
```
@1-5 > StudentRead simply has no password field.
@11 > The route declares response model StudentRead. Even though we return the whole dictionary, FastAPI only sends the fields in StudentRead.
@12-15 > The data lives in a dictionary for now. A real database arrives in level six, and response models get their own spotlight in level four.
