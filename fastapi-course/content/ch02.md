::: analogy Path vs query: an address vs shopping filters
> Here's the easiest way to tell them apart.
- 📍 A house address: Street 5, House 42 => **Path params** identify one thing: `/users/42`
> To find one specific house, you need its address. A path parameter does the same: it identifies one specific thing, like user forty two.
- 🛒 Shopping filters: under 500, colour red => **Query params** filter or sort: `/products?max_price=500`
> When you shop online, you add filters, like price under five hundred and colour red. Query parameters filter, sort and search.
- 🏠 No address, no delivery => Path params are always required
> Without an address, there's no delivery. So path parameters are always required.
- 🎛️ Filters are optional => Query params can have defaults
> But filters are optional, so query parameters can have default values.
L> So if I'm fetching one thing, it's the path. If I'm narrowing down a list, it's the query.
> That's the rule of thumb most teams use.
:::

::: code users.py | Path parameters and route order
```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/users/me")
def read_current_user():
    return {"user": "the current user"}


@app.get("/users/{user_id}")
def read_user(user_id: int):
    return {"user_id": user_id}
```
@11-13 > Here's a path parameter. user id comes from the URL, and the int hint converts it to a number.
@6-8 > And here's a fixed path, slash users slash me, for the logged in user.
@6 > Notice it's declared first. FastAPI checks routes from top to bottom, and the first match wins.
@11 L> What happens if I put the user id route first?
@11 > Then a request for slash users slash me would match user id first, FastAPI would try to turn me into a number, and you'd get a four twenty two.
@all > So the rule is: fixed paths first, parameterised paths after.
:::

::: code movies.py | Query parameters with defaults
```python
from fastapi import FastAPI

app = FastAPI()
MOVIES = [{"title": "Inception", "year": 2010}, {"title": "Dangal", "year": 2016}]

@app.get("/movies")
def list_movies(
    skip: int = 0,
    limit: int = 10,
    year: int | None = None,
):
    results = [m for m in MOVIES if year is None or m["year"] == year]
    return results[skip : skip + limit]
```
```output
GET /movies?year=2016&limit=5  ->  [{"title": "Dangal", "year": 2016}]
GET /movies?limit=abc          ->  422 (loc: ["query", "limit"])
```
@6-7 > Now query parameters. Any function parameter that isn't in the path becomes a query parameter.
@8-9 > skip and limit have defaults, so they're optional. They give us pagination.
@10 > year defaults to None, so the filter is applied only if the client sends it.
@12-13 > Inside, we filter by year and slice with skip and limit.
@out > Ask for the year two thousand sixteen, and only Dangal comes back. Send text for limit, and you get a four twenty two, and loc says the problem is in the query.
:::

::: concept Query parameter rules
visual: shield
- ❗ No default → **required**: `q: str`
> A query parameter without a default is required.
- 💤 `= None` → optional: `year: int | None = None`
> A default of None makes it optional.
- ✅ `bool` understands `true`, `1`, `yes`, `on`
> A bool parameter understands true, one, yes and on, in any letter case.
- 📚 Many values: a list type with `Query()` → `?tag=a&tag=b`
> And to accept the same parameter many times, like several tags, use a list type with Query.
:::

::: code movies.py | Validation with Annotated, Path and Query
```python
from typing import Annotated

from fastapi import FastAPI, Path, Query

app = FastAPI()


@app.get("/movies/{movie_id}")
def get_movie(
    movie_id: Annotated[int, Path(ge=1, description="Movie ID")],
    q: Annotated[str | None, Query(min_length=3, max_length=50)] = None,
):
    return {"movie_id": movie_id, "q": q}
```
@1-3 > Now real validation rules. Import Annotated, Path and Query.
@10 > Inside Annotated, first comes the type, then the rules. ge one means greater than or equal to one, so zero and negative IDs are rejected.
@11 > q is an optional search string, between three and fifty characters.
@all L> So all the rules live in the function signature?
@all > Yes. No if statements, no manual errors, and every rule appears in the docs automatically.
:::

::: tip Designing good URLs
- Use **nouns** for resources: `/movies`, not `/getMovies`
> Some design habits from real teams. Use nouns for resources, like slash movies, not slash get movies. The HTTP method is already the verb.
- Plural collections, ID in the path: `/movies/42`
> Use plural collection names, with the ID in the path.
- Filters, sorting and pagination go in the **query**
> Filters, sorting and pagination go in the query.
- Always cap `limit` so nobody downloads your whole database
> And always cap the limit, so nobody can download your whole database in one request.
```text
GET    /movies?genre=drama&limit=20
GET    /movies/42
POST   /movies
DELETE /movies/42
```
:::

::: code movies.py | Project solution: the search endpoint
```python
@app.get("/movies")
def list_movies(
    genre: Genre | None = None,
    year: int | None = None,
    min_rating: Annotated[float, Query(ge=0, le=10)] = 0,
    skip: Annotated[int, Query(ge=0)] = 0,
    limit: Annotated[int, Query(ge=1, le=50)] = 10,
):
    results = [
        m for m in MOVIES
        if (genre is None or m["genre"] == genre)
        and (year is None or m["year"] == year)
        and m["rating"] >= min_rating
    ]
    return {"total": len(results), "items": results[skip : skip + limit]}
```
@3-4 > Genre and year are optional filters.
@5 > The minimum rating is limited to zero through ten.
@6-7 > skip can't be negative, and limit is between one and fifty.
@9-14 > A list comprehension applies all the filters together.
@15 > And the response includes the total, plus the current page of items. You'll see this exact shape in real APIs.

::: interview junior
q: What is the difference between a path parameter and a query parameter? When do you use each?
- Path param identifies **one resource**: `/users/42`
> A path parameter identifies one specific resource, like user forty two.
- Query param **filters, sorts, searches or paginates**: `/users?role=admin`
> A query parameter filters, sorts, searches or paginates a collection.
- Path params are required; query params are usually optional
> Path parameters are required, while query parameters are usually optional with defaults.
- If removing it changes **what** you fetch, it's a path param
> My rule of thumb: if removing it changes which resource you're fetching, it belongs in the path.
