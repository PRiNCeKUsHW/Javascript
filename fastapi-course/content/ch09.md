::: analogy The event loop is like one fast waiter
> Imagine one very fast waiter serving the whole restaurant.
- 🍳 Order sent to the kitchen, waiter serves other tables => **`await`**: while waiting on I/O, other requests run
> The waiter sends an order to the kitchen, and serves other tables while it cooks. That's await: while one request waits for the database or the network, others keep moving.
- 🧍 The waiter stands at one table for ten minutes => A **blocking call** in `async def` freezes everyone
> Now imagine the waiter standing at one table for ten minutes. Every other table waits. That's a blocking call inside async def.
- 👥 Extra helpers for slow chores => Plain **`def`** endpoints run in a thread pool
> The restaurant also has helpers for slow chores. Plain def endpoints run in a pool of threads, so they don't freeze the waiter.
- 📮 "We'll text you when it's ready" => **Background work** after the response
> And for big orders: we'll text you when it's ready. That's background work after the response.
:::

::: code app/main.py | Blocking vs non-blocking
```python
import asyncio
import time

@app.get("/blocking")
async def blocking():
    time.sleep(1)           # blocks the whole event loop!
    return {"ok": True}

@app.get("/non-blocking")
async def non_blocking():
    await asyncio.sleep(1)  # other requests keep running
    return {"ok": True}

@app.get("/sync-ok")
def sync_ok():
    time.sleep(1)           # plain def runs in a thread pool
    return {"ok": True}
```
@4-7 > Three endpoints that each wait one second. The first is async def, but calls time dot sleep, which blocks.
@9-12 > The second awaits asyncio sleep, which gives control back to the event loop while waiting.
@14-17 > The third is a plain def. FastAPI runs it in a thread pool.
@all L> They all take one second. Does it matter?
@all > Let's measure it with ten requests at the same time.
:::

::: concept The async rules
visual: gears
- ✅ `async def` + `await` for async libraries: `httpx`, `asyncpg`, async SQLAlchemy
> Here are the rules. Use async def with await when your libraries are async, like httpx, asyncpg or async SQLAlchemy.
- ✅ Plain `def` for blocking libraries: `requests`, most SDKs, sync drivers
> Use plain def when you call blocking libraries, like requests or most cloud SDKs.
- 🚫 Never call blocking code inside `async def`
> Never call blocking code inside async def.
- 🧰 Stuck? `await run_in_threadpool(blocking_fn)`
> And if you must call a blocking function from async code, run it in the thread pool.
L> So async isn't automatically faster.
> Right. It's faster only when the waiting is truly async. Otherwise it can be much slower.
:::

::: mistake Blocking HTTP call inside async def
```python
import requests


@app.get("/weather/{city}")
async def weather(city: str):
    r = requests.get(f"https://api.example.com/weather/{city}")
    return r.json()
```
```python
@app.get("/weather/{city}")
async def weather(city: str, http: HttpDep):
    r = await http.get(f"https://api.example.com/weather/{city}")
    r.raise_for_status()
    return r.json()
```
@wrong > This is the real world version of the bug. requests is a blocking library, inside async def.
L> So if the weather service takes two seconds, my whole API stalls for two seconds?
> For every user, yes. And external services are often slow.
@right > Use an async client like httpx, and await it. Here it comes from a dependency, so we share one client for the whole app.
:::

::: code app/deps.py | One shared httpx client
```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(timeout=10)
    yield
    await app.state.http.aclose()


def get_http(request: Request) -> httpx.AsyncClient:
    return request.app.state.http


HttpDep = Annotated[httpx.AsyncClient, Depends(get_http)]
```
@1-5 > Create the client once in lifespan, and always set a timeout. Without one, a hanging service can hang your API too.
@8-9 > A tiny dependency hands the shared client to endpoints.
@12 > And HttpDep is the alias, just like SessionDep.
:::

::: concept When BackgroundTasks isn't enough
- ⚠️ Runs in the same process: lost if the server restarts
> BackgroundTasks is perfect for small, quick jobs. But it runs in the same process, so a restart loses it.
- 🔁 No retries, no scheduling, no progress tracking
> There are no retries, no scheduling, and no way to track progress.
- 🏭 Heavy or important jobs → a task queue: **Celery**, **ARQ**, **RQ**
> For heavy or important jobs, use a task queue like Celery, ARQ or RQ.
- 🧺 Jobs wait in Redis; separate workers process and retry them
> Jobs wait in Redis, and separate worker processes run them, with retries.
L> Like generating a big PDF report?
> Perfect example. Or resizing videos, or sending ten thousand emails.
:::

::: code worker.py | A task queue worker with ARQ
```python
from arq.connections import RedisSettings


async def generate_report(ctx, user_id: int) -> None:
    ...  # minutes of work, retried if it fails


class WorkerSettings:
    functions = [generate_report]
    redis_settings = RedisSettings(host="redis")
    max_tries = 3


@router.post("/reports", status_code=202)
async def request_report(user: CurrentUser, request: Request):
    job = await request.app.state.arq.enqueue_job("generate_report", user.id)
    return {"job_id": job.job_id}
```
@4-5 > The job is a normal async function, run by a separate worker process.
@8-11 > WorkerSettings lists the jobs, where Redis lives, and how many times to retry.
@14-17 > The API only enqueues the job and returns a two oh two, accepted, with a job id the client can check later.

::: code app/main.py | Middleware: request IDs and timing
```python
@app.middleware("http")
async def add_request_id_and_timing(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID", str(uuid.uuid4()))
    start = time.perf_counter()
    response = await call_next(request)
    elapsed_ms = (time.perf_counter() - start) * 1000
    response.headers["X-Request-ID"] = request_id
    response.headers["X-Process-Time-Ms"] = f"{elapsed_ms:.1f}"
    return response


app.add_middleware(GZipMiddleware, minimum_size=1000)
```
```output
X-Request-ID: abc-123
X-Process-Time-Ms: 3.8
Content-Encoding: gzip
```
@1-2 > Middleware wraps every request. It runs before your route, and again after.
@3 > Reuse the caller's request ID, or create one. You'll see it in every log line in level twelve.
@4-6 > call next runs the rest of the app, and we time it.
@7-9 > Then we add both headers to the response.
@12 > And GZip middleware compresses large responses automatically.
@out L> So when a user reports a bug, they can send me the request ID?
@out > Exactly, and you can find every log line for that one request.

::: concept Middleware or dependency?
- 🧅 **Middleware**: every request, around the whole app
> When do you use middleware, and when a dependency? Middleware runs for every request, around the whole app.
- 🔧 Good for: request IDs, timing, CORS, compression, security headers

- 🎯 **Dependencies**: per route, with typed results and docs
> Dependencies run per route, give typed results, and show up in the docs.
- 🔑 Good for: auth, DB sessions, pagination, permissions

::: code app/api/v1/tasks.py | Project solution: a safe external call
```python
@router.get("/{task_id}/holiday-check")
async def holiday_check(task: OwnedTaskDep, http: HttpDep):
    url = f"https://date.nager.at/api/v3/PublicHolidays/{task.due.year}/IN"
    try:
        r = await http.get(url)
        r.raise_for_status()
    except httpx.HTTPError:
        raise HTTPException(status_code=503, detail="Holiday service unavailable")
    holidays = {h["date"] for h in r.json()}
    return {"due": task.due, "is_holiday": task.due.isoformat() in holidays}
```
@2 > Here's the interesting part of my solution. The task comes from an ownership checked dependency, and the client from HttpDep.
@4-6 > We await the call, and check the status.
@7-8 > Any network error or timeout becomes a clear five oh three, not a hanging request or a confusing five hundred.
@9-10 > Then we check the due date against the list of holidays.
