::: concept Sync TestClient or async httpx?
- 🧪 **`TestClient`**: simple, sync tests, great to start
> Which client should you use? TestClient is simple and synchronous, perfect for getting started.
- ⚡ **`httpx.AsyncClient` + `ASGITransport`**: `async def` tests
> When your tests need to await things, like async database setup, use httpx AsyncClient with ASGI transport.
- 🔁 Same `.get()`, `.post()`, `.json()` API for both
> Both have the same get, post and json methods, so switching is easy.
- ⚠️ Only `with TestClient(app)` runs `lifespan`
> One surprise: only TestClient used in a with block runs your lifespan. ASGI transport skips it.
L> So my startup code, like creating the shared http client, doesn't run?
> Exactly. We'll handle that with overrides in a minute.
:::

::: code tests/conftest.py | A fresh database for every test
```python
@pytest.fixture
async def session_factory():
    engine = create_async_engine("sqlite+aiosqlite://", poolclass=StaticPool)
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    yield async_sessionmaker(engine, expire_on_commit=False)
    await engine.dispose()
```
@1 > A fixture is setup code that pytest runs for you. Any test that names it as a parameter gets it.
@3 > We create an in-memory SQLite database. StaticPool keeps one shared connection, so the data stays alive during the test.
@4-5 > Create all the tables.
@6 > Yield hands the session factory to the test.
@7 > After the test, everything after yield runs, and the database is thrown away.
@all L> So every single test starts with empty tables?
@all > Yes. No test can break another test by leaving data behind.
:::

::: code tests/conftest.py | The client fixture with an override
```python
@pytest.fixture
async def client(session_factory):
    async def override_session():
        async with session_factory() as session:
            yield session

    app.dependency_overrides[get_session] = override_session
    transport = httpx.ASGITransport(app=app)
    async with httpx.AsyncClient(transport=transport, base_url="http://test") as c:
        yield c
    app.dependency_overrides.clear()
```
@2 > Fixtures can use other fixtures. The client needs the session factory.
@3-5 > We write a replacement for get session, that opens sessions on the test database.
@7 > dependency overrides is a dictionary. Every route that asked for get session now gets ours instead. This is why dependencies make FastAPI so testable.
@8-10 > Then an async client that talks to the app in memory.
@11 > And after the test, we clear the overrides. Remember this line, it's today's bug.
:::

::: mistake Overrides that leak between tests
```python
def test_admin_can_delete(client):
    app.dependency_overrides[get_current_user] = fake_admin
    r = client.delete("/tasks/1")
    assert r.status_code == 204
    # override never removed...
```
```python
@pytest.fixture
def as_admin():
    app.dependency_overrides[get_current_user] = fake_admin
    yield
    app.dependency_overrides.pop(get_current_user)


def test_admin_can_delete(client, as_admin):
    r = client.delete("/tasks/1")
    assert r.status_code == 204
```
@wrong > Here, a test sets a fake admin user, and never removes it.
L> It passes, so what's the problem?
> Every test that runs after it is also logged in as admin. A test that checks members can't delete tasks will pass, even if the security is broken. And the result changes with the test order.
@right > Put overrides in a fixture with yield, and remove them after. Now the fake admin only exists inside the tests that ask for it.
:::

::: code tests/conftest.py | A fixture that logs users in
```python
@pytest.fixture
async def auth_headers(client):
    async def make(email="riya@example.com", password="secret123"):
        await client.post("/auth/register", json={"email": email, "password": password})

    return make
```
@1-2 > Almost every test needs a logged in user, so we make a fixture for it.
@3 > It returns a small function, a factory, so one test can create several users.
@4-5 > It registers through the real endpoints, and logs in.
@6 > And returns the header, ready to use.
@all L> Why use the real signup endpoint instead of inserting a user directly?
@all > Because then the test also proves signup and login work. If they break, many tests go red together.

::: code tests/test_tasks.py | Faking an external API
```python
def fake_http(handler):
    async def override():
        async with httpx.AsyncClient(transport=httpx.MockTransport(handler)) as c:
            yield c
    return override


async def test_holiday_api_down_is_503(client, auth_headers):
    def handler(request):
        raise httpx.ConnectTimeout("too slow")

    app.dependency_overrides[get_http] = fake_http(handler)
    headers = await auth_headers()
    r = await client.post("/tasks", json={"title": "Trip", "due": "2026-03-04"}, headers=headers)
    r = await client.get(f"/tasks/{r.json()['id']}/holiday-check", headers=headers)
    assert r.status_code == 503
```
@1-5 > Remember the holiday API from level nine? In tests we never call the real internet. MockTransport lets a plain function answer every request.
@8-10 > Here, our fake API simulates a timeout.
@12 > We override get http with the fake client. The client fixture clears it after the test.
@13-16 > And we check our app answers a clean five oh three.
@all L> So I can test the API being down, without actually taking it down.
@all > Yes, and it runs in milliseconds, even with no internet.

::: tip Make async coverage accurate
