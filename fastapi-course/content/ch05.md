::: analogy Depends is like a chef's supplier
> Picture a chef in a busy restaurant kitchen.
- 👨‍🍳 The chef lists the ingredients needed => Your endpoint **declares** what it needs with `Depends`

- 🚚 The supplier delivers before cooking => FastAPI **runs the dependency first** and passes the result in
> The supplier delivers before cooking starts. FastAPI runs the dependency first, and passes the result into your function.

::: code deps.py | Your first dependency
```python
from typing import Annotated

from fastapi import Depends, FastAPI

app = FastAPI()

def pagination(skip: int = 0, limit: int = 10) -> dict:
    return {"skip": skip, "limit": min(limit, 100)}


@app.get("/books")
def list_books(page: Annotated[dict, Depends(pagination)]):
    return {"page": page}


@app.get("/authors")
def list_authors(page: Annotated[dict, Depends(pagination)]):
    return {"page": page}
```
@7-8 > A dependency is just a function. This one reads skip and limit from the query, and caps the limit at a hundred.
@12 > The endpoint declares page with Depends pagination. FastAPI runs pagination first and passes in the result.
@17 > And the same dependency is reused for authors. The logic lives in one place.
@17 L> So if I need to change the max limit, I change it once?
@17 > Exactly, and every endpoint gets the fix.
:::

::: code deps.py | Class dependencies and a reusable alias
```python
class Paginator:
    def __init__(self, skip: int = 0, limit: int = 10):
        self.skip = skip
        self.limit = min(limit, 100)

    def apply(self, items: list) -> list:
        return items[self.skip : self.skip + self.limit]


PageDep = Annotated[Paginator, Depends()]


@app.get("/books")
def list_books(page: PageDep):
    return page.apply(BOOKS)
```
@1-4 > A dependency can also be a class. FastAPI reads the init parameters from the query.
@6-7 > And a class can carry helper methods, like apply.
@10 > This line is worth remembering. PageDep is an alias. Depends with nothing inside means: build whatever the type says.
@14-15 > Now any endpoint just writes page colon PageDep. Big codebases use aliases like this everywhere.
:::

::: code auth.py | Sub-dependencies: a user from an API key
```python
API_KEYS = {"key-123": "riya"}


def get_api_key(x_api_key: Annotated[str, Header()]) -> str:
    if x_api_key not in API_KEYS:
        raise HTTPException(status_code=401, detail="Invalid API key")
    return x_api_key


def get_current_user(key: Annotated[str, Depends(get_api_key)]) -> str:
    return API_KEYS[key]


@app.get("/me")
def read_me(user: Annotated[str, Depends(get_current_user)]):
    return {"user": user}
```
@4 > Dependencies can have their own dependencies. This one reads a header. The underscore name becomes the x dash api dash key header automatically.
@5-7 > A wrong key raises a four oh one, and the endpoint never runs.
@10-11 > get current user depends on get api key. That's a sub dependency.
@14-16 > And the endpoint only asks for the current user. Checking keys and finding users all happens behind the scenes.
:::

::: flow How FastAPI resolves the chain
visual: plug
- 📨 Request with X-API-Key
> Here's the chain. A request arrives with an API key header.
- 🔑 get_api_key
> get api key runs first.
- 👤 get_current_user
> Then get current user, using its result.
- 🎯 read_me endpoint
> And finally your endpoint, with a ready to use user.
- 🛑 A 401 stops the chain early
> If anything in the chain raises an error, everything after it is skipped.

::: code db.py | yield dependencies: setup and cleanup
```python
class Connection:
    def __init__(self):
        print("open connection")

    def close(self):
        print("close connection")

def get_db():
    db = Connection()
    try:
        yield db
    finally:
        db.close()


@app.get("/stats")
def stats(db: Annotated[Connection, Depends(get_db)]):
    return {"ok": True}
```
@8-9 > Some things must be opened and then closed, like a database connection. That's what yield dependencies are for.
@10-11 > The code before yield is the setup. The yielded value goes to the endpoint.
@12-13 > The code in finally is the cleanup. It runs after the response, even if the endpoint raised an error.
@16-17 > In level six we'll use this exact pattern for real database sessions.
:::

::: mistake The leaking connection
```python
def get_db():
    db = Connection()
    yield db
    db.close()
```
```python
def get_db():
    db = Connection()
    try:
        yield db
    finally:
        db.close()
```
@wrong > This looks fine, and it works in a quick demo.
L> Until the endpoint raises an error?
> Exactly. Then the close line never runs. The connection leaks, and after a few hundred errors your database refuses new connections.
@right > Wrap the yield in try and finally, and the cleanup runs no matter what.
:::

::: code test_me.py | Overrides make testing easy
```python
from fastapi.testclient import TestClient


def fake_user() -> str:
    return "test-user"


app.dependency_overrides[get_current_user] = fake_user
client = TestClient(app)

assert client.get("/me").json() == {"user": "test-user"}
app.dependency_overrides.clear()
```
@4-5 > In a test, you don't want real API keys. Write a fake.
@8 > dependency overrides says: whenever get current user is needed, call fake user instead.
@11 > Now the test passes without any key.
@12 > And clear the overrides afterwards, so other tests aren't affected.
L> That's so much easier than mocking everything.
> It's one of the main reasons teams love FastAPI. We'll go deep on testing in level ten.

::: concept Dependencies at every level
- 🎯 One endpoint: a parameter with `Depends(...)`
> A dependency can apply to one endpoint,
- 🗂️ A whole router: `APIRouter(dependencies=[Depends(require_admin)])`
> to a whole router, for example every admin route,
- 🌍 The whole app: `FastAPI(dependencies=[Depends(verify_key)])`
> or to the entire app.
- ⚡ Same dependency twice in one request? It runs **once**
> And if the same dependency is needed twice in one request, it only runs once. The result is cached.
:::

::: tip Keep dependencies fast and focused
- Put shared aliases in one `deps.py`: `SessionDep`, `CurrentUser`
> Some habits from production codebases. Keep shared aliases in one deps file.
- Keep them small: one job each
> Keep each dependency small, with one job.
- No heavy work in a dependency: it runs on every request
> Avoid heavy work, because it runs on every single request.
- App-wide resources (pools, clients) go in `lifespan`, not in a dependency
> And create app wide resources, like connection pools and HTTP clients, once at startup, not per request.

```python
# deps.py
SessionDep = Annotated[AsyncSession, Depends(get_session)]

```

::: code deps.py | Project solution: member and admin checks
```python
API_KEYS = {
    "key-riya": {"name": "Riya", "role": "member"},
    "key-asha": {"name": "Asha", "role": "admin"},
}


def current_member(x_api_key: Annotated[str, Header()]) -> dict:
    member = API_KEYS.get(x_api_key)
    if member is None:
        raise HTTPException(status_code=401, detail="Invalid API key")
    return member


def require_admin(member: Annotated[dict, Depends(current_member)]) -> dict:
    if member["role"] != "admin":
        raise HTTPException(status_code=403, detail="Admins only")
    return member
```
@1-4 > Here's my solution. The keys live in a dictionary for now. In a real app they'd be in the database.
@7-11 > current member finds the member by key, or raises a four oh one.
@14-17 > require admin builds on it, and raises a four oh three for non admins.
:::
