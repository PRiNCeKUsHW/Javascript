::: title
- HTTP status codes made simple
- `response_model`: send only what you should
- `HTTPException` for 404s and friends
- Custom exceptions and handlers
- One consistent error format
> Level four में आपका स्वागत है।
> आज हम सीखेंगे कि API सही status code के साथ जवाब कैसे दे, और errors को professional तरीके से कैसे handle करें।
:::

::: analogy Status codes are like courier tracking updates
> Status codes को courier की tracking updates की तरह समझिए।
- ✅ "Delivered" / "New order booked" => **2xx success**: 200 OK, 201 Created, 204 No Content
> Delivered या new order booked, यानी सब ठीक। Two hundreds का मतलब success, जैसे two hundred OK और two zero one created।
- 📮 "Wrong address" / "Already booked" => **4xx client errors**: 400, 404, 409, 422
> Wrong address या duplicate booking, यानी गलती customer की तरफ़ से है। Four hundreds client errors होते हैं।
- 🔐 "Show your ID" / "Staff only" => **401** not logged in, **403** not allowed
> ID दिखाइए, यानी four zero one, आप logged in नहीं हैं। Staff only, यानी four zero three, logged in हैं लेकिन permission नहीं है।
- 🔥 "Our truck broke down" => **5xx server errors**: our bug, not the client's
> और truck ख़राब हो गया, यानी गलती हमारी है। Five hundreds server errors हैं, जिन्हें हमें fix करना है।
:::

::: code users.py | response_model: never leak secrets
```python
from fastapi import FastAPI
from pydantic import BaseModel, EmailStr

app = FastAPI()


class UserIn(BaseModel):
    email: EmailStr
    password: str


class UserOut(BaseModel):
    email: EmailStr


@app.post("/users", response_model=UserOut, status_code=201)
def create_user(user: UserIn):
    return user
```
@7-9 > Client sign up के लिए email और password भेजता है।
@12-13 > लेकिन वापस हम सिर्फ email भेजना चाहते हैं।
@16 > इसलिए route पर response model UserOut लगाया। और status code two zero one, क्योंकि नया user create हुआ।
@17-18 > अब function पूरा user return कर रहा है, password के साथ। फिर भी FastAPI response को UserOut के हिसाब से filter करेगी, और password बाहर नहीं जाएगा। यही response model की ताकत है।
:::

::: code notes.py | HTTPException: proper 404s
```python
from fastapi import FastAPI, HTTPException, status

app = FastAPI()
NOTES = {1: {"id": 1, "text": "Buy milk"}}


@app.get("/notes/{note_id}")
def get_note(note_id: int):
    note = NOTES.get(note_id)
    if note is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail=f"Note {note_id} not found",
        )
    return note
```
@1 > Error भेजने के लिए HTTPException और status module import कीजिए। status में सारे codes नाम के साथ हैं, ताकि magic numbers ना लिखने पड़ें।
@9-10 > Note नहीं मिला, तो
@11-14 > HTTPException raise कीजिए, status four zero four और एक साफ़ message के साथ।
@11 > ध्यान दीजिए, raise किया है, return नहीं। Raise करते ही function वहीं रुक जाता है, चाहे कितना भी अंदर के function से हो।
:::

```python
@app.delete("/notes/{note_id}", status_code=status.HTTP_204_NO_CONTENT)
```

@1 > Delete successful हो तो क्या भेजें? Common choice है two zero four, no content।
@2-4 > Function कुछ return नहीं करता, और body खाली जाती है। Note ना मिले, तो four zero four।

::: code errors.py | Custom exceptions and handlers
```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()


class DuplicateError(Exception):
    def __init__(self, field: str):
        self.field = field


@app.exception_handler(DuplicateError)
async def duplicate_handler(request: Request, exc: DuplicateError):
    return JSONResponse(
        status_code=409,
        content={"error": {"code": "duplicate", "field": exc.field}},
    )
```
@7-9 > बड़े projects में अपने exceptions बनाइए, जैसे DuplicateError। ये normal Python exception है, इसमें HTTP का कुछ नहीं।
@12-13 > फिर exception handler register कीजिए। अब code में कहीं भी DuplicateError raise हो, FastAPI ये function चलाएगी।
@14-17 > और handler एक साफ़ four zero nine response बनाता है। Business logic HTTP से अलग रहता है, जो clean architecture के लिए बहुत अच्छा है।
:::

::: concept Which status code when?
- **400** a business rule failed: "cannot cancel a shipped order"
> Four hundred, जब कोई business rule fail हो, जैसे shipped order cancel करना।
- **404** the resource doesn't exist
> Four zero four, जब resource ही नहीं है।
- **409** conflict: duplicate email, version clash
> Four zero nine, conflict, जैसे duplicate email।
- **422** the input shape is invalid (FastAPI sends this for you)
> Four twenty two, input का format गलत है, जो FastAPI खुद भेजती है।
- **500** a bug: log it, never show the stack trace to users
> और five hundred, यानी bug। उसे log कीजिए, लेकिन user को कभी stack trace मत दिखाइए।
:::

::: recap
- Use the right status code: 201 create, 204 delete, 404, 409, 422
> Recap। सही status code use कीजिए, create पर two zero one, delete पर two zero four।
- `response_model` or a return type filters what leaves your API
> Response model या return type से तय कीजिए कि API से क्या बाहर जाएगा।
- `raise HTTPException(status_code, detail)` stops the request
> HTTPException raise करते ही request वहीं रुक जाती है।
- Custom exceptions + `@app.exception_handler` keep logic clean
> Custom exceptions और handlers से business logic साफ़ रहता है।
- Keep one error format for the whole API
> और पूरी API में errors का एक ही format रखिए।
:::

qsay: सवाल नंबर तीन. Database का user object बिना response model के return करना ख़तरनाक क्यों है?

> और कल अगर database में नया column जुड़ा, तो वो भी चुपचाप public हो जाएगा।
- `response_model` is an allow-list: only declared fields go out
> Response model एक allow list की तरह है। सिर्फ declared fields ही बाहर जाती हैं।

::: practice
q: Make any unexpected error return `{"error": {"code": "internal"}}` with status 500, without leaking the stack trace.
qsay: सवाल नंबर पाँच. कोई भी unexpected error हो, तो error code internal के साथ five hundred return कीजिए, लेकिन stack trace leak किए बिना।

```python
@app.exception_handler(Exception)
```

::: code errors.py | Project solution: one error format
```python
def error(status: int, code: str, message: str) -> JSONResponse:
    body = {"error": {"code": code, "message": message}}
    return JSONResponse(status_code=status, content=body)


class NoteExists(Exception):
    pass


@app.exception_handler(NoteExists)
async def note_exists(request: Request, exc: NoteExists):
    return error(409, "note_exists", "A note with this title already exists")


@app.exception_handler(HTTPException)
async def http_error(request: Request, exc: HTTPException):
    return error(exc.status_code, "http_error", str(exc.detail))
```
@1-3 > Solution में पहले एक छोटा helper, जो हर error को same format में बनाता है।
@6-12 > फिर NoteExists exception, और उसका handler, जो four zero nine भेजता है।
@15-17 > और HTTPException के लिए भी handler, ताकि four zero four भी उसी format में आए।
:::

::: code notes.py | Project solution: create with a duplicate check
```python
class NoteIn(BaseModel):
    title: str = Field(min_length=1, max_length=80)
    text: str = ""

class NoteOut(NoteIn):
    id: int

NOTES: dict[int, NoteOut] = {}

@app.post("/notes", response_model=NoteOut, status_code=201)
def create_note(note: NoteIn):
    if any(n.title == note.title for n in NOTES.values()):
        raise NoteExists()
    note_id = len(NOTES) + 1
    NOTES[note_id] = NoteOut(id=note_id, **note.model_dump())
    return NOTES[note_id]
```
@1-6 > NoteIn में title और text, और NoteOut में साथ में id।
@12-13 > Create से पहले check कीजिए कि same title पहले से तो नहीं। है, तो NoteExists raise।
@14-16 > वरना नई id के साथ note save कीजिए और two zero one के साथ return। बाकी routes भी इसी pattern पर बनेंगे, वो आप खुद complete कीजिए।

::: interview junior
q: What is the difference between 401 Unauthorized and 403 Forbidden?
- **401**: the client is not authenticated (missing or invalid credentials)
> Four zero one का मतलब है client authenticate नहीं हुआ, token नहीं है या गलत है।
- **403**: authenticated, but lacks permission for this action
> Four zero three का मतलब है user पहचाना गया, लेकिन उसे ये काम करने की permission नहीं है।
- 401 should come with a `WWW-Authenticate` header
> Four zero one के साथ standard के हिसाब से WWW Authenticate header भी भेजा जाता है।
:::

::: interview junior
q: What does `response_model` do in FastAPI?
qsay: What does response model do in FastAPI?
- Validates and **filters** the response data to the declared fields
> Response model response को validate करता है और सिर्फ declared fields तक filter करता है।
- Prevents leaking secrets like password hashes
> इससे password hash जैसी secret चीज़ें leak नहीं होतीं।
- Documents the response shape in OpenAPI
> और docs में response का exact format दिख जाता है।
- A return type annotation does the same job
> Function का return type annotation भी यही काम करता है।
:::

::: interview mid
q: How would you return consistent error responses across a large FastAPI application?
- Define one error envelope, for example `{"error": {"code", "message"}}`
> सबसे पहले एक error format तय कीजिए, जैसे error के अंदर code और message।
- Domain exceptions in services, mapped by `@app.exception_handler`
> Services में domain exceptions raise कीजिए, और exception handlers उन्हें HTTP responses में बदलें।
- Override handlers for `HTTPException` and `RequestValidationError` too
> HTTPException और validation errors के handlers भी override कीजिए, ताकि सब एक जैसा दिखे।
- Machine-readable `code` values help frontend and mobile teams
> Code field machine readable हो, ताकि frontend team उसके हिसाब से message दिखा सके।
:::

::: interview mid
q: When would you raise `HTTPException`, and when a custom exception with a handler?
qsay: When would you raise HTTP Exception, and when a custom exception with a handler?
- `HTTPException` in route code for simple HTTP cases (404, 403)
> Route के अंदर simple cases के लिए HTTPException ठीक है, जैसे four zero four।
- Custom exceptions in the service/business layer, which shouldn't know HTTP
> लेकिन service layer को HTTP के बारे में पता नहीं होना चाहिए। वहाँ custom exceptions use कीजिए।
- Handlers translate them in one place: easy to test and reuse
> फिर handlers उन्हें एक ही जगह HTTP में बदलते हैं। Testing भी आसान, और वही service CLI या background job में भी reuse हो सकती है।
:::

::: interview senior
q: How do you handle unexpected exceptions in a production FastAPI service?
- A catch-all handler returns a safe 500, never a stack trace
> एक catch all handler, जो safe five hundred response दे, stack trace कभी नहीं।
- Log the traceback with a request ID and context
> Logs में पूरा traceback, request ID और context के साथ, ताकि debugging आसान हो।
- Send errors to monitoring (Sentry, OpenTelemetry) and alert on spikes
> Errors को Sentry या OpenTelemetry जैसे monitoring tool में भेजिए, और error rate बढ़े तो alert।
- Keep expected errors (4xx) separate from bugs (5xx) in dashboards
> और dashboards में expected four hundreds और असली bugs वाले five hundreds को अलग रखिए। ये production maturity दिखाता है।
