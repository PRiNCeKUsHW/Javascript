L> Errors are the part I usually skip.

::: analogy Status codes are like courier tracking updates
> Think of the tracking updates on a parcel.
- ✅ "Delivered" or "new order booked" => **2xx success**: 200 OK, 201 Created, 204 No Content
> Delivered, or new order booked: everything worked. Codes in the two hundreds mean success.
- 📮 "Wrong address" or "already booked" => **4xx client errors**: 400, 404, 409, 422
> Wrong address, or already booked: the problem is on the customer's side. Four hundreds are client errors.
- 🔐 "Show your ID" or "staff only" => **401** not logged in, **403** not allowed
> Show your ID is a four oh one: we don't know who you are. Staff only is a four oh three: we know you, but you're not allowed in.
- 🔥 "Our truck broke down" => **5xx server errors**: our bug, not the client's
> And our truck broke down is a five hundred. That's our bug, and we have to fix it.
L> So a five hundred is always our fault?
> Always. A healthy API sends five hundreds almost never, and we'll see how to make sure they don't leak details.
:::

::: code users.py | response_model: never leak secrets
```python
from fastapi import FastAPI
from pydantic import BaseModel, EmailStr

app = FastAPI()


class UserIn(BaseModel):
    email: EmailStr
    password: str


class UserOut(BaseModel):
    email: EmailStr


@app.post("/users", response_model=UserOut, status_code=201)
def create_user(user: UserIn):
    return user
```
@7-9 > The client signs up with an email and a password.
@12-13 > But we only want to send the email back.
@16 > So the route declares response model UserOut, and status code two oh one, because a new user was created.
@17-18 > The function returns the whole user, password included. But FastAPI filters the response through UserOut, so the password never leaves the server.
:::

::: mistake Leaking the password hash
```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    user = db.get_user(user_id)
    return user
```
```python
@app.get("/users/{user_id}")
def get_user(user_id: int) -> UserOut:
    user = db.get_user(user_id)
    return user
```
@wrong > Here's a real security incident waiting to happen. The endpoint returns the database user directly, with no response model.
L> And the database user has the password hash in it.
> Right. The hash, internal flags, and any column someone adds next month. All of it goes straight to the client.
@right > Add a return type, or a response model, and FastAPI only sends the fields in UserOut. Think of it as an allow list for your output.
:::

::: code notes.py | HTTPException: proper 404s

```python
app = FastAPI()

```

::: code errors.py | Custom exceptions and handlers
```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

app = FastAPI()


class DuplicateError(Exception):
    def __init__(self, field: str):
        self.field = field


@app.exception_handler(DuplicateError)
async def duplicate_handler(request: Request, exc: DuplicateError):
    return JSONResponse(
        status_code=409,
        content={"error": {"code": "duplicate", "field": exc.field}},
    )
```
@7-9 > In bigger apps, define your own exceptions, like DuplicateError. It's plain Python, with nothing about HTTP.
@12-13 > Then register an exception handler. Wherever DuplicateError is raised, FastAPI calls this function.
@14-17 > The handler builds a clean four oh nine response.
@12 L> Why not just raise an HTTPException with four oh nine?
@12 > Because your business logic shouldn't know about HTTP. The same service code can then be reused in a background job or a command line tool.

visual: shield
- 🧾 **400** a business rule failed

- 🔍 **404** the resource doesn't exist

::: tip One error format for the whole API
- Pick one shape and use it everywhere
> A pro tip from real teams. Pick one error shape and use it everywhere.
- A machine-readable `code` plus a human `message`
> Include a machine readable code, so the frontend can react to it, and a human message.
- Handle `HTTPException` and validation errors the same way
> And make HTTPException and validation errors use the same shape.

```json
}
```

::: code errors.py | Project solution: one error format
```python
def error(status: int, code: str, message: str) -> JSONResponse:
    body = {"error": {"code": code, "message": message}}
    return JSONResponse(status_code=status, content=body)


class NoteExists(Exception):
    pass


@app.exception_handler(NoteExists)
async def note_exists(request: Request, exc: NoteExists):
    return error(409, "note_exists", "A note with this title already exists")


@app.exception_handler(HTTPException)
async def http_error(request: Request, exc: HTTPException):
    return error(exc.status_code, "http_error", str(exc.detail))
```
@1-3 > Here's my solution. A small helper builds every error in the same shape.
@6-12 > The NoteExists exception and its handler send a four oh nine.
@15-17 > And a handler for HTTPException makes four oh fours use the same shape too.

::: code notes.py | Project solution: create with a duplicate check
```python
class NoteIn(BaseModel):
    title: str = Field(min_length=1, max_length=80)
    text: str = ""

class NoteOut(NoteIn):
    id: int

NOTES: dict[int, NoteOut] = {}

@app.post("/notes", response_model=NoteOut, status_code=201)
def create_note(note: NoteIn):
    if any(n.title == note.title for n in NOTES.values()):
        raise NoteExists()
    note_id = len(NOTES) + 1
    NOTES[note_id] = NoteOut(id=note_id, **note.model_dump())
    return NOTES[note_id]
```
@1-6 > NoteIn has a title and text, and NoteOut adds the id.
@12-13 > Before creating, check for a duplicate title, and raise NoteExists if there is one.
@14-16 > Otherwise, save the note with a new id and return it with a two oh one. The other routes follow the same pattern, so finish them yourself.
